# 推理部署与服务

## 一句话结论

把语言模型部署成服务，本质是"把这些东西从电力转化成Token再转化成智能"：请求进来先被调度、查 KV 缓存、再执行核心 ML 代码（prefill 与 decode）。prefill（预填充）是算力密集的"大输入小输出"操作，decode（解码）是内存带宽受限的"一次一个 token"操作，两者计算特性截然相反，因此推理引擎必须在请求调度、连续批处理、KV 缓存三级存储（GPU→CPU DRAM→SSD/磁盘）与队列之间做取舍，在交互式 SLO（如"不到一秒的时间内拿到第一个token"）与吞吐/成本（需要多少 GPU、能同时服务多少个会话）之间权衡。到了"每天服务数万亿甚至更多的token"的规模，还会暴露小规模永远遇不到的稀有 bug、单卡故障容错、以及以路由与内核为代表的工程优化空间。

## 核心概念

- **推理引擎（inference engine）**：把电力转化为智能的引擎，"推理才是关键"；推理引擎与 GPU 内核"才是真正把GPU从沙子变成我们今天能用的东西的关键"。演讲者认为"如果你理解了推理,理解了推理引擎,理解了作为许多核心技术基础的GPU内核,你就能在机器学习算法中实现全战创新"。
- **Token 生命周期（推理服务流水线）**：请求→被调度→查询 KV 缓存（看是否见过该请求/变体、能否省计算）→执行核心 ML 代码（prefill/decode）→输出 token→停止检查/安全检查→返回；引擎在一个循环里"等待这些请求进来,执行token采样的循环并不断重复"。
- **工作负载形态（workload shape）**：输入/输出 token 分布因工作负载而异——编码（"几万个输入token"）、摘要、整本书对话、标准聊天、多轮 agent 工作流各不相同；"这些因素开始定义你的工作负载是什么样的"。
- **SLO（服务等级协议）**：不同应用有不同时间要求，例如交互式应用"希望在不到一秒的时间内拿到第一个token"（TTFT），或"我知道自己将要生成500个token,我希望整个响应能在一定时间内返回"。
- **Prefill（预填充）**：计算密集型操作，"1万个token输入只输出一个token"，"prefill类似只是不运行反向传播"，可充分利用 GPU。
- **Decode（解码）**：一次只生成一个 token，"非常受内存带宽限制"，"每次你都得把整个模型加载进来,就只是为了生成一个token"。
- **连续批处理（continuous batching，ASR 原词"连续P处理"）**：同一时刻在 GPU 上并行处理多个请求，共享计算与 KV 缓存内存；GPU 内存耗尽时请求开始排队。
- **KV 缓存**：利用前缀共享避免为每个用户重复计算；采用传统树（trie，ASR"jada结构"）结构记录哪些 token 见过、哪些是新的；运行期目标是"尽可能把kv缓存做得越大越好"。
- **KV 缓存分层存储**：GPU 内存→CPU DRAM（ASR"DRM"）→磁盘/SSD（ASR"瓷盘"）逐级卸载，关心各级读取速度。
- **请求调度/路由**：决定把请求放到哪些 GPU、是否命中缓存、冷/热请求、prefill/decode 分别送往哪些机器组；"这个请求会被调度"。
- **Prefill/Decode 分离（disaggregation）**：把预填充和解码拆分到不同的 GPU/机器组，因为"他们各自的计算瓶颈和计算特性差异非常大"，可以专门化两类计算。
- **容错（fault tolerance）**：模型拆到 64/72 个 GPU 上为百万用户服务时，"单个GPU当机怎么办?能否让它具备容错能力?"。
- **硬件协同设计（co-design）**：按部署目标芯片选量化格式（NVFP4 vs MXP4）、按芯片内存调整模型大小"让它能放得进去,还要留出足够的KV缓存之类的空间"。
- **每参数智能（per-parameter intelligence）**：更少参数意味着推理时"你可以容纳更多的KV缓存"、分布在更少 GPU 上减少通信量，是成本与质量权衡的核心。

## 工作机制

### 1. 请求如何穿过推理服务（Token 生命周期）

- 请求先被调度："你可能会用到各种不同的GPU,把预填充和解码分别放在不同的机器上来做"。
- 查缓存："你会用这个请求去查询KV缓存,看看我之前是否见过这个请求或它的变体,有没有什么计算是我可以节省下来的"。
- 执行 ML 代码：可以"把计算任务拆分到不同的机器上,或者拆分到不同的节点上"，或"根据模型的大小和拆分方式,把计算并行到不同的GPU上"。
- 分词后进入"有点复杂的调度机制"："比如我之前见过这些token吗?我能不能直接从缓存中查找一些激活值?"。
- 输出处理：检查停止 token 或跑安全检查——"看看用户是不是在试图以恶意方式入侵系统之类的"。
- 引擎主循环："推理引擎实际上是在一个循环中运行,等待这些请求进来"。

### 2. 工作负载形态决定 SLO 与优化目标

- 编码工作负载：输入很长（"几万个输入token"），输出可能是"思考token"或简短内容，取决于训练方式。
- 时间要求分层：快速交互聊天（语音模式 ChatGPT）"可能需要相对快速的响应"；agent 工作流让模型自己迭代，对话轮次之间"可能出现一个间隔"。
- 关键描述量："每次你输入了多少新的token,以及每次你要生成多少个token"、会话时长、用户粘性（"是不是那种粘性很强的用户会跟Cloud Agent反复来回交流"）、对话间隔。
- 目标："我希望在不到一秒的时间内拿到第一个token"；"我希望整个响应能在一定时间内返回,这样我的用户就能快速阅读它"。

### 3. Prefill 与 Decode：两种相反的计算特性

- Prefill："1万个token输入只输出一个token,这属于计算密集型操作"，"跟你们在训练阶段关注的那些事情其实非常接近"。
- Decode："decode就是指你一次只生成一个token"，"非常受内存带宽限制"——"每次你都得把整个模型加载进来,就只是为了生成一个token"。
- 时间结构："育田充通常比单个解码步骤要长得多,但你会运行更多的解码步骤"（每提示一次 prefill，每 token 一次 decode）。
- 因此"一个非常基本的优化我们几乎都开始采用的做法是,你在一组工作节点上运行育田充,在另一组工作节点上运行解码"。

### 4. 连续批处理与请求队列

- 多个请求同时占用两类资源："你得一次性同时处理多个请求,这些请求也可能是内存资源,如果你正在填满kv缓存"。
- 长短请求交错：短请求可能一个步骤就完成，新长请求"可能又是一个非常长的请求"。
- 内存耗尽→排队："你的gpu内存不够,需把所有kv缓存存到gpu上内存可能耗尽,然后你会因某种原因开始排队,等那个长请求处理完之后,你就可以开始一个新的请求"。
- "当系统中有许多不同的请求同时存在时,会带来一些复杂性"。

### 5. KV 缓存：前缀共享与三级存储

- 复用动机："你不需要为每一个用户都重新计算新的机构处值"（ASR 原词，指激活值）；用户上传长书只需跑一次预填充，后续补充无需整本书重算。
- 前缀共享实现："我们有一种叫做kv缓存的机制,它利用前缀共享"；"采用一个非常传统的jada结构来处理,就像一棵基础的树,看看哪些token我之前见过,哪些token是新的"。
- 目标最大化缓存："你希望尽可能把kv缓存做得越大越好"，"最好能够缓存来自许多不同用户的请求,或者来自同一个用户跨多个绘画的请求,并且能够同时运行尽可能多的绘画"。
- 三级存储："你先把kv缓存存在GPU上,然后很快就用光了GPU的内存"，"下一步你就可以把它存到CPU的DRM里了"，再"把更多的kv缓存放到瓷盘上"（SSD）。也因此关心 CPU 与 SSD 读取速度。
- 成本视角：CPU 拖累——"如果你那台价值50万美元的机器被一个你花1000美元买来,装在上面的CPU给拖了后腿,那可不是什么好情况"；"OpenAI把全球的SSD和DRAM都买光了,部分原因就是为了像这样的情况"。

### 6. 缓存驱逐与调度（操作系统类比）

- 驱逐策略：长期不用的 token "可能会把它驱逐出去,送到CPU上或者送到瓷盘里,又或者送到某个其他的全局存储中"。
- 明确与操作系统同构："我相信你们应该都没上过操作系统课吧?你们应该去上操作系统这门课,因为你们真的会学到一些非常经典的调度问题"；示意图"完全就像你在七八十年代可能见过的操作系统示意图"——"如果你在电脑上打开太多应用程序,CPU内存就会耗尽,然后你就得把这些应用放到磁盘上去。这正是相同的工作负载。"。
- LRU 与预测预取：LRU（"最近最少使用算法"）"性能可以达到最优方案的两倍以内"；理想是"如果你能预测未来……让我先去把那段内存预取进来"，例如"当你打开聊天应用翻出一个一个月前的旧对话时,这就是一个非常强烈的信号"；否则"那就用各种启发式方法"。
- 最终目标："你当然希望尽可能多地服务流量"。

### 7. Prefill/Decode 分离与专用硬件

- 做法与动机："我们通常会把育田充和解码这两个阶段拆分到不同的GPU上,也就是不同的机器组上"，因为两者"计算瓶颈和计算特性差异非常大"；prefill 能"真正充分利用你的GPU"，decode 则"对内存带宽的要求非常高"。
- 硬件趋势：decode 与 prefill 差异大到"如果你专注于解码,你可以使用完全不同的芯片"——NVIDIA "使用其GPU来处理预填充部分,而使用这些LPO GROG芯片来处理解码"（GROG 指 Groq 的 LPU）；"OpenAI和Cerebras有计算方面的合作,这种芯片的解码能力要强得多"；"其他公司,比如Sabanova之类的"也在布局。
- 模型拆分选项：万亿参数模型跑在 280GB GPU 上可"把每个张量切成四份……这被称为张量并行"，或把 MoE 专家"拆分到不同的GPU上"；"你在这个阶段做出的选择将决定瓶颈在哪里,以及你需要多少GPU来运行你的模型,你能同时服务多少个绘画"。

### 8. 规模化部署的工程挑战：稀有 Bug 与容错

- 稀有 bug："当你真正开始大规模部署这些推理引擎时,也就是当你开始每天服务数万亿甚至更多的token时,你就会开始遇到一些非常棘手的bug"；"那些在小规模下运行的很好的东西,一旦到了大规模就难免会开始出问题"。
- 概率与症状："发生概率在0.001或更低的时间，其中一些可能会变成NAN"——logits 变 NaN 后"模型会开始输出相同的标记性"，出现"嗨嗨嗨嗨嗨"式重复或感叹号循环。
- 工具调用 bug：某引擎处理工具调用出错，"其症状是补权长度急剧增加"，陷入"持续数万个token的死亡循环"。
- 中文乱码 bug：模型"毫无理由的突然随机开始输出中文字符"，最初被归咎于量化问题，实际"只是其中一个kernel里有一个差异错误"——"有时你在运行attention时会从GPU中读取到一些额外的未初始化的内存空间"。
- 容错与硬件可靠性：NVL72（"这些是72个GPU通过非常快速的互联连接在一起"）拆分万亿模型时要"开始考虑容错问题"；故障原因包括连接器脆弱（"它们是塑料做的,而不是金属的"）、"他们把风扇放进了芯片里"。
- 规模化的关键问题："如果我把一个模型拆分到64个GPU上为百万用户万亿Token的生产流量提供服务,单个GPU当机怎么办?能否让它具备容错能力?"；百万级上下文窗口时"你是把这个上下文拆分到多个不同的GPU上吗?"。

### 9. 路由级优化（以 CATCO Prefill/Decode 分离为例）

- 观察：多轮对话平均十轮时"大约10%的请求会是全新的"；新请求"会有数千个Token,它的样子会变得非常不同,而且计算成本也会高得多"。
- 问题："你通常不会希望把这个预填充任务与一个正在进行到一半的简短对话放在一起处理"。
- 方案："搭建一个非常简单的路由器……如果有一个新请求进来,它的缓存命中率非常低,就把它发送到一组GPU上,这样他们可以一起处理这些任务,然后把所有其他热请求发送到另一组预填充节点上"。
- 收益："通过这些非常非常简单的优化,服务速度可以提升高达40%"。
- 阶段定位：这些技术研究"还在非常早期的阶段"，"10年20年后人们回顾起来会说,哦,这些人当时为什么在讨论这个?这不是已经很明显了吗?"。

### 10. 成本经济学与硬件协同设计

- 推理引擎=把电力转化为智能："推理引擎GPU内核,这些才是真正把GPU从沙子……变成我们今天能用的东西的关键"；"GPU是新石油"，"数千亿,甚至更多的资金投入到GPU上"。
- 成本由部署选择决定：拆分方式决定"你需要多少GPU来运行你的模型,你能同时服务多少个绘画"；KV 缓存占用内存是持续成本，小模型更灵活——"如果你参数更少,你就可以容纳更多的KV缓存,或者因为你需要将模型分布在更少的GPU上而减少通信量等等"。
- 协同设计：按目标芯片调整模型——"如果你知道自己要把一个模型部署到某个特定的Ciribra Trip上……调整模型的大小让它能放得进去,还要留出足够的KV缓存之类的空间"；"那些正在推出的中国模型……可能已经开始考虑那些即将推出的华为芯片了"。
- 量化格式随硬件："如果你打算在英伟达的GPU上部署一个模型,就像他们发布的Nemotron模型那样,你就会用NVFP4这种格式来训练它"；"如果你不打算在英伟达芯片上运行,比如你是AMD,那你就会用另一种叫做MXP4的格式"。
- 解码内核成本：让解码接近光速（H100 上"实现了72%的带宽利用率"）的 mega kernel 编写"需要投入大量的汗水和心血"——"一个非常有才华的内核工程师,在一年内大概能为一个硬件两到三个模型编写P处理大小从1到16的Mega Kernel"。
- 架构对服务的取舍：agent 循环工作流"要尽可能保持你的KV缓存是热的"；大规模一次性批处理（每文档只看一次）"KV缓存就不一定那么重要了"；DeepSeek MLA 是"非常激进的压缩方式"；KV 用 FP8/FP4 是"相当大的差异"；非因果（双向）模型适合不需要生成大量 token 的批处理（"一旦你得到了向量就把它存入数据库"），而"聊天工作流就不一样了。它的处理过程里总是会有一个解码的环节"。

## 示例或代码

**课程给出的具体数字（可审计）：**
- 编码工作负载输入"几万个输入token"；对话平均十轮时约 10% 请求为全新请求。
- 交互式 SLO："不到一秒的时间内拿到第一个token"；"知道自己将要生成500个token"要求整段在时限内返回。
- 万亿参数模型跑在"280gb的GPU"上，需张量并行（每张量切四份）或 MoE 专家拆分。
- NVL72："72个GPU通过非常快速的互联连接在一起"；容错场景示例为"拆分到64个GPU上为百万用户万亿Token的生产流量提供服务"。
- 稀有 bug 概率："发生概率在0.001或更低"。
- CATCO：路由层"两行代码"级优化，服务速度提升"高达40%"。
- H100 上 mega kernel "实现了72%的带宽利用率,这已经接近GPU上的光速了"。
- 硬件协同设计例子：NVIDIA Nemotron 用 NVFP4（英伟达专有 FP4 格式），AMD 用 MXP4。
- 内核人力成本："一年内大概能为一个硬件两到三个模型编写P处理大小从1到16的Mega Kernel"。

**伪代码（基于课程描述整理，非引文）：**

推理引擎主循环（服务侧视角）：
```
loop:
    req = next_request()                 # 等待请求进来
    route(req)                           # 调度：选 GPU 组 / 查 KV 缓存命中
    if cache_hit(prefix(req)):           # "我之前见过这些token吗?"
        reuse_activations(prefix)
    prefill(req)                         # 大输入→1 token，算力密集，可连续批处理
    while not stop_token:
        token = decode_one(req)          # 一次一个 token，内存带宽受限
        check_stop_or_safety(token)      # 检查停止 token / 安全检查
        append_to_kv_cache(token)        # 更新 KV 缓存
```

KV 缓存分级与驱逐（服务侧视角）：
```
if kv_cache 超出 GPU 内存: 迁移到 CPU DRAM
if 仍超出: 迁移到 SSD/磁盘              # "把更多的kv缓存放到瓷盘上"
if 需要驱逐: LRU 驱逐长期不用的 token    # "送到CPU上或者送到瓷盘里"
if 可预测未来: 预取相关对话段到 GPU      # 打开旧对话 = 强信号
```

## 常见误区

- **误区：推理和训练是同一类计算。** 澄清：prefill 与训练类似（算力密集、可充分利用 GPU），但 decode 是内存带宽受限的串行小计算，两者"计算瓶颈和计算特性差异非常大"。
- **误区：KV 缓存只存在 GPU 上。** 澄清：KV 缓存按 GPU 内存→CPU DRAM→磁盘/SSD 三级存放，读完 GPU 内存会"把它存到CPU的DRM里了"，再"把更多的kv缓存放到瓷盘上"。
- **误区：小规模验证通过，大规模自然没问题。** 澄清："那些在小规模下运行的很好的东西,一旦到了大规模就难免会开始出问题"——0.001 概率的 kernel 差异错误（如随机输出中文字符）只有日服务数万亿 token 时才会暴露。
- **误区：把所有请求混在一起批处理吞吐最高。** 澄清：新的大请求与进行到一半的短对话混批不好——"你通常不会希望把这个预填充任务与一个正在进行到一半的简短对话放在一起处理"，冷/热请求分流（CATCO）可提升 40% 服务速度。
- **误区：模型大小只影响训练成本。** 澄清：推理时"一个很大的瓶颈其实出在GPU内存上"，"如果你参数更少,你就可以容纳更多的KV缓存"、减少跨 GPU 通信，"更小的模型会给你带来很大的灵活性"。
- **误区：预填充和解码应该放在同一组 GPU 上。** 澄清：标准做法是"把育田充和解码这两个阶段拆分到不同的GPU上,也就是不同的机器组上"，甚至可以为此用完全不同的芯片（Groq LPU、Cerebras）。
- **误区：所有 LLM 工作负载都一样。** 澄清：agent 循环工作流"要尽可能保持你的KV缓存是热的"，而大规模一次性批处理"KV缓存就不一定那么重要了"；聊天工作流"总是会有一个解码的环节"，双向批处理模型则没有。
- **误区：量化格式选择与部署无关。** 澄清：部署目标是"你在哪家芯片上跑"——英伟达用 NVFP4、AMD 用 MXP4，模型发布时的量化格式选择反映其部署意图（"那些正在推出的中国模型"暗示考虑华为芯片）。
