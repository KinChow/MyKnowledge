# CUDA 编程模型

## 一句话结论

CS336 第 5 讲以"程序员视角"讲 GPU 编程模型：把 GPU 看作一台由大量轻量级线程（组织为 thread → block → warp 三级）执行 SIMT 指令的**吞吐量机器**；内存呈层次（寄存器/本地 → 共享内存 → 全局内存），"一旦你超出了共享内存的范围"操作就会急剧变慢，因此写高效算子的全部要义就是**减少全局内存移动**——通过合并访问、分块复用、算子融合、重计算、低精度等手段实现。课程几乎不教裸 CUDA API（未出现 threadIdx/blockIdx/__syncthreads/银行冲突），而是借 PyTorch/JAX/Torch.compile 等高层次抽象与 Flash Attention 实例讲透"硬件如何工作 → 算子如何写快"。硬件原理（SM、缓存、Tensor Core 等）由另一文档 [[llm-gpu-hardware]] 覆盖，本文档专注编程模型与 kernel 编写；并可与现有 wiki 页 [[cpp-concurrent-programming-and-cuda]]（含 thread/block/grid、warp、bank conflict、开发流程）互补印证。

## 核心概念

- **线程（thread）**：GPU 中并行运行、执行工作的轻量级执行单元；遵循 SIMT 模型——所有线程执行相同指令、各有不同输入。
- **线程块（block）**：一组线程；一个块保证在单个 SM 上运行，可访问该 SM 的共享内存池，块内线程可重复使用相同内存片段。
- **线程束（warp，转录误写为"线程数"）**：32 个连续编号线程为一组的执行单元，是 GPU 内部调度的基本单元，可降低调度器开销。
- **SIMT（转录误写为"CMT/3MT"）**：Single Instruction Multiple Threads，一条指令多条线程；遇到 if/else 分支时所有线程都会执行两个分支（控制分歧）。
- **寄存器（register）**：速度最快、最本地的存储，用于存放数组起始/结束地址等信息。
- **本地内存（local memory）**：只限于单个流多处理器（SM）内部使用。
- **共享内存（shared memory）**：线程块内部可访问、程序员可编程的内存，用于线程间传递/复用数据。
- **全局内存（global memory / HBM / DRAM）**：芯片外部大容量内存（H200 的 144GB 显存即指它），按突发段读取、访问慢（比 L1 慢约 10 倍）。
- **合并访问（coalescing）**：一个 warp 内所有线程落在同一突发段，一次读取免费带回整段数据。
- **分块（tiling）**：把数据切成瓦片加载进共享内存、反复复用，减少全局内存读取。
- **算子融合（fusion）**：把多个算子合并成一个单一 kernel，只读写全局内存一次。
- **重计算（recomputation）**：反向传播丢弃激活值、用时重算，以算力换内存。
- **低精度（low precision）**：FP32→BF16→FP8/FP4；位数减半则内存移动减半。
- **屋顶线模型（roofline）**：吞吐量在运算强度低时受内存限制（对角区）、高时受计算限制（平坦区）。

## 工作机制

1. **三级线程组织**：线程（并行执行工作的基本单元）→ 块（一组线程，保证在单个 SM 上运行并绑定其共享内存池）→ warp（32 个线程一组，是 GPU 内部调度的基本单元）。
2. **内存层次**：寄存器/本地内存（SM 内）→ 共享内存（块内）→ 全局内存（芯片外 DRAM）。"一旦你超出了共享内存的范围"操作就"变得非常慢"，因此"通过合理分组线程块来减少全局内存的读取次数"是贯穿本次讲座的核心策略。
3. **SIMT 执行**：所有线程执行相同的指令；if/else 是"控制分歧"——两个分支都会执行、另一侧被屏蔽闲置，因此尽量少写 if，改用零乘/掩码。
4. **屋顶线思维**：让代码落在计算受限的平坦区 = 提高运算强度 = 减少每单位计算的内存移动。
5. **六大优化技巧**：SIMT 友好（避免 if/控制分歧）、低精度、算子融合、重计算、合并访问、分块；其中多数本质是"减少内存移动"。
6. **综合实例**：Flash Attention = 分块 + 重计算 + 在线 softmax，把 HBM 访问降到次二次级别。

## 示例或代码

转录未给出任何可运行的 CUDA kernel 代码（无 __global__/threadIdx/blockIdx 等语法），只给概念性示例：

- **分块矩阵乘法**：把两个矩阵切成 2×2 子矩阵，先把 m00、n00 两个分块加载进共享内存，"我完全在这些子矩阵上操作"，算完把输出分块写回。
- **分块算术**：n×n 朴素乘法中"我的每个输入元素都需要被读取n次"；用大小为 t 的分块后，每个输入先从全局内存读 n/t 次、分块内再读 t 次；t=n 时全局只读 1 次。
- **低精度算术强度**：float32 下两个长度为 N 的数组，"每个操作四个字节，总共八个字节的内存访问，我只有一个Flop的操作量"，即每 Flop 8 字节；降精度后每操作所需字节数减少。
- **工厂/传送带比喻（算子融合）**：多个算子 = 多次把原材料运进运出工厂，占大量双向内存带宽；融合 = 一个大型工厂，只付两次内存带宽。
- **填充案例**：Karpathy 做 nanoGPT 速度优化时把词表"从5257增加到50304，结果获得了25%的加速"——为对齐突发段而填充的反直觉例子。

## 常见误区

- **误区：GPU 线程像 CPU 线程一样各走各的分支。** 澄清：SIMT 下所有线程执行相同指令；遇到 if/else 时两个分支都会执行，不匹配的线程被屏蔽闲置，即"控制分歧"。因此"你真的不想写EF语句"，而是"用零相成或者用掩码相成"。
- **误区：共享内存 = L1 缓存。** 澄清：缓存是自动存储"最近访问过"数据元素的机制、程序员无法控制；共享内存是"可编程的元素"，可往里放、往外取。
- **误区：为什么不把整个芯片都用共享内存/SRAM 建。** 澄清：它"要跪上几百倍"（贵）、功耗大，实用加速器必须用内存层次结构并高效利用。
- **误区：矩阵越大吞吐量越高。** 澄清：矩阵乘法吞吐量会出现"特定尺寸下，矩阵乘法比其他尺寸慢得多"的奇怪现象，根源是分块整除性、突发段对齐、SM 数（1792→1793 时块数 98→120，A100 的 108 个 SM 放不下导致骤降）。
- **误区：2 的幂有魔力。** 澄清："这其实并不是因为2的密次方有什么魔力之类的"——16/32 只是足够大、正好适配突发窗口特性（能被突发大小整除）。
- **误区：低精度是免费午餐。** 澄清：需弄清每个操作该用哪种格式（矩阵乘法权重/激活可低精度、softmax 需 FP32）；量化/反量化有开销、收益被稀释，FP8 训练可省约 20%–30% 计算量，但"不会带来两倍的加速"。

## 详细章节

### 从 CPU 到 GPU：延迟 vs 吞吐量

"CPU是为快速串行执行而设计的"，处理复杂分支与控制流，拥有很大的控制单元、少量能执行数学或其他运算的 ALU，追求低延迟；GPU 真正关注的是吞吐量，"靠的是拥有大量轻量级的核心"，数百个计算单元封装在一个芯片上并行执行，"这是一种非常不同的编程和思考模式"。规模上，一个 A100 有 128 个 SM（转录分块章节另称 108，见待验证项），每个 SM 内部又有多个流处理器可并行执行不同线程。历史脉络上，频率缩放（转录"Dinar的定律"即 Dennard 缩放）约在 2000 年见顶，此后靠横向扩展、并行执行指令，这就是 GPU 的故事。

### 线程组织：thread / block / warp（"线程数"）

GPU 执行模型有三个角色：线程是并行执行工作的轻量级单元；线程块"保证在单个SM上运行"，因而能访问该 SM 的共享内存池（"块可以访问一个共享的内存池"）；warp（转录误写为"线程数"）"线程以32个连续编号为一组执行"，"这是32个线程一起执行的基本单元"，是"GPU内部调度的一个基本单元"，减少了调度器决定运行哪些线程时的开销。线程总是非常轻量，"它们可以随时被停止或启动"，调度器发现另一个 warp 更适合运行就暂停当前 warp，任务切换很快，用切换掩盖延迟、换取吞吐量。

### 内存模型：寄存器 / 本地 / 共享 / 全局

设备代码从寄存器读取数据（寄存器最快最本地，可存放数组起始/结束地址）；本地内存只限于单个流多处理器内部使用；共享内存在线程块内部被访问，"或者有一些信息要在多个线程里重复使用，那这些数据就应该放在共享内存里"；全局内存是"距离较远的DRM"（芯片外），访问需承受传输延迟；还有常量内存（转录称"我在各种编程实践中见的不多"）与主机内存间来回传输（处理超出 GPU 显存的数据）。"这个内存模型最关键的一点就是，一旦你超出了共享内存的范围，那么操作就会变得非常慢"，因此"通过合理分组线程块来减少全局内存的读取次数，将是贯穿本次讲座的核心策略"。全局内存即高级程序员通常认为的 GPU 内存（如 H200 的 144GB 显存）。

### 共享内存 vs 缓存：可编程 vs 自动

L1 缓存与共享内存很快（访问约 20–30 个周期），全局内存"比L1缓存要慢上10倍"，差别对运行速度影响非常大。区分点在于：缓存只是自动存储"最近访问过的数据元素"的机制、程序员无法控制；"共享内存是一个可编程的元素"，可以往里放东西、从里面取东西。为什么不用共享内存构建整个芯片？因为它"要跪上几百倍"（贵）、功耗大，实用加速器必须依赖内存层次结构并高效利用。例外是"被英伟达收购的Grook"（Groq），"它的设计就是有大量的SRAM"，对推理很有帮助，但对大多数加速器而言仍要遵循层次结构才能跑得快。

### 编写 kernel 的要点：SIMT 与分支（控制分歧）

所有线程执行相同指令（SIMT）；若在 GPU 代码里写 if，则"实际上每个线程都会执行EF和Else这两个分支"，不属于该分支的线程把计算屏蔽掉、闲置等待，形成"很大的计算间隙"，"这就是为什么你真的不想写EF语句的原因之一"。真实 GPU 代码"经常"发现"在用零相成或者用掩码相成，而不是做一个EF语句来更新一半"——乘法一次性完成，而分支可能要等时钟周期。编程风格上，写底层代码（如 PTX）时"你不是在编程每个线程，而是说，这是我的指令和输入，现在在所有输入上执行它们"，类似 apply/函数式编程。

### 屋顶线模型与运算强度

"这就是屋顶线模型"：吞吐量在某个点前受内存限制（"我们是受内存限制的"，给再多算力吞吐量也不上升），之后受计算限制（"因为我已经被矩阵惩罚单元完全饱和了"），曲线呈现"内存限制的对角区域"与"计算限制的平坦区域"。"如果你想确保你的代码在GPU上高效运行，那你真正需要做的就是让它处在这个平坦的部分"，即提高运算强度——每次内存读取对应的计算量要足够高，让计算单元饱和。

### 六大优化技巧总览

课程讲六种技巧：第一个"在风格上有点不同"的是 SIMT 友好（避免 if/控制分歧）；其余"都会带有尽可能减少内存移动这种风格"：低精度（"你从FP32开始，然后到BF06再到Indate，你只是不断降低数字的精度"；位数减半则"就只需要移动一半的比特"）、算子融合（把多个算子合成"一个单一的能执行所有这些操作的内核"，"编译器可以自动为你完成这项工作"，如 Torch.compile/JAX）、重计算（反向传播中"直接丢弃所有的激活值"、用时重算，把示例中的内存访问从 8 次降到 5 次）、合并访问、分块。总结："如何让机器学习在GPU上跑得更快，其实很大程度上就是关于内存内存"——减少访问次数、合并读取、复用数据、用其他资源（算力）换内存。

### 合并访问与 DRAM 突发段

全局内存是 DRAM，"以突发的方式来访问"：访问第一个位置时"我可以免费读取所有这四个初始值"，因为内存单元按块排列、激活一次放大器几乎免费读出整块（突发数据可达 128 字节）。合并访问（coalescing）"这个词指一个warp内所有线程落在同一突发段"。对行主序矩阵，索引沿行递增、沿主轴（列）方向移动的线程不会合并，一次读取会免费带回整行数据；翻转/重排（行主序 vs 列主序）可让每个线程在一次内存读取中完成其读取，显著改善从大型连续结构读数据的性能。

### 分块与矩阵乘法

分块被"特意留到最后"、被认为是"对性能堆叠的影响"最大的技巧："尽可能的把内存访问操作分组到一起"，把空间切成一块块瓦片，"每块瓦片都会加载到我的共享内存里"，加载后反复从共享内存读取做尽可能多的计算。矩阵乘法中"我的每个输入元素都需要被读取n次"；用大小为 t 的分块后，每个输入先从全局内存读 n/t 次、块内再读 t 次（t=n 时全局只读 1 次），"用大共享内存分块能大幅减少矩阵乘法等操作的全局内存访问"。

### 分块导致的"奇怪现象"：整除性、填充、SM 数

分块大小是"需要优化的参数"：矩阵尺寸"需能被分块大小整除"、最好是 2 的幂且能被 32 整除（转录"密"为"幂"误写）；分块与突发段不对齐时至少得读两个分块才能读出目标数据，需填充让突发段边界与分块大小对齐。案例一：Karpathy 做 nanoGPT 速度优化时把词表"从5257增加到50304，结果获得了25%的加速"——为了对齐而填充的反直觉例子。案例二：矩阵从 1792 到 1793，256×128 分块数从 98 变 120，而 A100 只有 108 个 SM：98 刚好放得下、120 放不下（多出一批 12 个分块、处理时大部分 GPU 空闲），吞吐量骤降。结论："16或32足够大，具备了合适的突发窗口特性"，"这其实并不是因为2的密次方有什么魔力之类的"，而是可整除/对齐带来的。

### GPU 编程与 CPU 编程的差异（写算子）

差异可归纳为五点：设计目标（低延迟 vs 高吞吐）；编程模型（串行分支 vs SIMT 同指令多输入）；线程成本（重量级 OS 线程 vs 轻量级、可随时被调度器启停的 GPU 线程）；内存（统一大内存 vs 层次化，共享内存之外皆慢）；性能瓶颈（早期是算力，如今是内存/通信）。"如果你是在GPU编程的早期阶段，你可能不会太在意内存"，但现在"计算能力和内存之间的差距变得越来越大"，"越往右走，内存和通信的瓶颈就会越来越明显"，因此今天讲的优化基本都是内存优化，一切都要尊重内存层次结构、尽可能把数据放进共享内存而非全局内存。

### Flash Attention：分块 + 重计算 + 在线 softmax

作为"把所有内容整合起来"的实例：朴素 PyTorch 注意力"变为一个巧妙融合的单一内核"，"很多性能提升都来自于减少了从HBM也就是全局内存传输的数据量"。做法是"应用分块和重计算"，使内存访问达到次二次级别。难点是注意力有一个全局 softmax（"因为Morphix是全局操作，把所有元素连在一起"），解法是在线（online）softmax："你一边计算皈依化的Morphs crew一边进行排序"（"皈依化"为归一化、"Morphs crew"为 softmax 的 ASR 误写），跟踪当前最大值、遇到更大值就替换并修正，逐分块计算、保留部分累加（放在共享内存/寄存器），最后与 V 分块相乘再做除法；反向传播则丢弃 n² 激活、逐分块重算。

### 课程对高层抽象的态度与 Triton 空缺

课程路线是"理解硬件 → 用高层框架写好算子"：推荐资源（Horace 博客、GPU Mode 社区、Google 团队 GPU 书）用于理解硬件；编译器可自动做简单融合（"Torch Compile是PyTorch编译器"、"两者都会将基本操作融合成单个CVA调用"，CVA 为 CUDA 的 ASR 误写）；分块被视为"底层系统问题"，"除非你是在编写自己的内核"，通常只需关心矩阵尺寸等。转录全篇未提 Triton——"用 Triton 等抽象替代裸 CUDA"是期望的连接点，但本讲未覆盖（见待验证项）。
