# 正交设计四原则

## 一句话结论

正交设计四原则是指导软件走向**高内聚低耦合**、减少变更影响的四条准则：**最小化重复、分离变化、缩小依赖范围、向稳定方向依赖**。它们互为补充——重复意味着耦合，变化应预留稳定接口，依赖应尽量缩小范围，并总是面向稳定（抽象）方向依赖。

## 核心概念

- **最小化重复**：重复意味着耦合；重复的代码需要修改时容易出现漏改。
- **分离变化**：识别变化方向并对变化预留扩展接口；扩展接口必须反映变化方向的本质特点（稳定接口），多个接口不能纠缠在一起。
- **缩小依赖范围**：最小化知识原则；依赖接口，不要依赖实现；接口应该尽可能包含少的知识。
- **向稳定方向依赖**：定义 API 时关注 what 而不是 how，站在需求/用户的角度定义 API，而不是站在实现者的角度。接口是抽象的、稳定的，实现是不稳定的。

## 工作机制

四条原则从不同维度把"变化"与"稳定"分离，让系统更容易演进：

1. **最小化重复** 解决"重复代码漏改"的耦合问题——消除重复即消除一处修改需多处同步改动的场景。
2. **分离变化** 要求识别变化方向、预留反映其本质的稳定扩展接口，使新变化通过扩展而非改动接入。
3. **缩小依赖范围** 通过"依赖接口而非实现、接口包含尽量少的知识"来降低模块间的知识耦合。
4. **向稳定方向依赖** 确保依赖总是流向稳定的一侧——API 面向需求（what）定义、面向用户定义，因为抽象是稳定的、实现是不稳定的。

四者共同服务于高内聚低耦合：消除重复、隔离变化、最小化知识、锚定稳定。

## 示例或代码

- **最小化重复**：重复代码（如复制粘贴的校验逻辑）抽取为公共方法/模块；当业务规则变化时只需改一处。
- **分离变化**：对可能变化的策略（如排序算法、支付方式）定义稳定接口，新增实现类即可扩展，不改动调用方。
- **缩小依赖范围**：模块 A 通过接口 `IDataSource` 依赖数据源，而不是直接依赖某个具体实现类；接口只暴露必要的方法。
- **向稳定方向依赖**：设计 API 时从"调用方需要什么"出发定义方法签名（what），而不是从"实现怎么做"出发暴露内部细节（how）。

## 常见误区

- **把"消除重复"理解为消灭所有重复**：参考简单设计四原则，"尽可能消除重复"实际是"最小化重复"，并非所有重复都可消除。
- **把"分离变化"变成过度设计**：为不会变化的方向预埋接口，违背 YAGNI；应识别真实的变化方向再预留扩展点。
- **接口设计面向实现**：站在实现者角度暴露细节、或让接口纠缠多个职责，都违背"缩小依赖范围"与"向稳定方向依赖"。

## 详细章节

### 正交四原则

#### 最小化重复

重复意味着耦合；当重复的代码需要修改时，容易出现漏改的情景



#### 分离变化

识别变化方向并对变化预留扩展接口。而这个扩展接口必须反映变化方向的本质特点（稳定接口），为了更好复用和使用的简洁性，多个接口不能纠缠在一起



#### 缩小依赖范围

最小化知识原则；依赖接口，不要依赖实现；接口应该尽可能包含少的知识



#### 向稳定方向依赖

定义API时应该关注what，而不是how，站在需求的角度去定义API，而不是实现的方式定义API。要站在用户的角度去定义API，而不是站在实现者的角度。因为接口是抽象的，是稳定的，实现是不稳定的
